# /autofix — разбор тикета поддержки

## Зачем это нужно

Прецедент, из-за которого появился этот регламент: пользователь прислал
скриншот ошибки «сеть оборвалась при загрузке части» при загрузке файла с
явно слабого мобильного соединения (~4 KB/s было видно на скриншоте
статус-бара). Гипотеза «слабая сеть» выглядела правдоподобно и была
подкреплена визуальным доказательством — поэтому её приняли как
единственную, выкатили retry с backoff и отчитались как о решённой
проблеме.

Ошибка осталась. Реальная причина — CORS S3-бакета разрешал загрузку
только с `http://localhost:3000`, а прод к этому моменту уже отвечал на
другом origin. Браузер блокировал каждый PUT-запрос ещё до отправки, и
`XMLHttpRequest` показывал это как `xhr.onerror` — неотличимо от обрыва
связи. Правдоподобная гипотеза со скриншотом-«доказательством» оказалась
неверной именно потому, что альтернативы не проверялись.

Отсюда наказ: **никогда не доверять одной гипотезе**. Здесь это не
пожелание — API `/admin/tickets/{id}/events` физически не даст перевести
тикет в `fix_ready`, пока не выполнено:

- гипотез записано не меньше трёх;
- ни одна не осталась `pending`;
- хотя бы одна `confirmed`;
- у каждой `rejected` заполнено `evidence` — чем проверялась и что
  показала проверка.

Правило живёт в `backend/app/tickets.py::check_can_close` и покрыто
тестами в `backend/tests/test_ticket_rules.py` — можно свериться с кодом,
если формулировка здесь разойдётся с реализацией.

## Модель данных

- **Ticket** — заявка: `number`, `description`, `page_url`,
  `screenshot_s3_key`, `status` (`new` → `investigating` → `fix_ready` →
  `deployed`, либо тупиковые `rejected`/`need_info`).
- **TicketEvent** — таймлайн, который видит пользователь: смена статуса +
  сообщение. Именно из этих сообщений пользователь узнаёт, что происходит
  с его заявкой — писать их понятно и по-русски.
- **TicketHypothesis** — пул версий: `text`, `verdict`
  (`pending`/`confirmed`/`rejected`), `evidence`.

## Как подключиться

Авторизация — обычный JWT администратора:

```bash
API=https://5-42-98-64.sslip.io  # или текущий адрес прода/локали
TOKEN=$(curl -s -X POST "$API/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"<admin_email>","password":"<admin_password>"}' | jq -r .access_token)
```

## Последовательность

### 1. Забрать тикет

```bash
curl -s "$API/admin/tickets?status=new" -H "Authorization: Bearer $TOKEN"
curl -s "$API/admin/tickets/<id>" -H "Authorization: Bearer $TOKEN"
```

Ответ включает `recent_activity` — действия автора тикета за час до и
минуту после подачи заявки (журнал из `backend/app/activity_log.py`).
Смотреть его первым делом: часто там уже виден upload_started без
upload_completed, dialog_question_asked без ответа и т.п. — прямая
подсказка, на чём сфокусировать гипотезы.

### 2. Воспроизвести

Открыть `screenshot_url` из ответа, попробовать повторить сценарий
локально/на том же окружении, что и у пользователя (прод — раз жалоба с
прода). Не воспроизвелось — это тоже результат, который нужно
зафиксировать с доказательством, а не повод тихо закрыть тикет.

### 3. Записать пул гипотез — до первой проверки

```bash
curl -s -X POST "$API/admin/tickets/<id>/hypotheses" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"text": "CORS бакета не пускает текущий origin"}'
```

Минимум три, из **разной** природы, чтобы пул не был вариациями одной и
той же догадки:

- клиент (браузер, JS-код, состояние формы);
- сеть/окружение (CORS, DNS, TLS, прокси, скорость соединения);
- бэкенд (логика роута, валидация, миграция схемы);
- данные (конкретная запись/пользователь в необычном состоянии);
- внешний сервис (S3, SpeechKit, AI Gateway, Telegram — down или
  вернул неожиданный ответ).

Писать пул целиком, пока не начали проверять первую версию — иначе список
неизбежно подгоняется под то, что уже "нашли", и перестаёт быть
независимым набором.

### 4. Для каждой — дешёвый различающий тест

Прежде чем проверять, сформулировать: что увижу, если гипотеза верна, и
что — если нет. Годится: curl с реальными заголовками окружения, чтение
логов (`docker logs`, `/admin/error-logs`, `/admin/activity`), точечный
unit-тест, проверка конфигурации (`.env`, CORS-политика бакета через
`boto3.get_bucket_cors`), сравнение с рабочим окружением.

### 5. Проставить вердикты

```bash
curl -s -X PATCH "$API/admin/tickets/<id>/hypotheses/<hyp_id>" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"verdict": "confirmed", "evidence": "get_bucket_cors показал только localhost:3000 в AllowedOrigins"}'
```

`rejected` без `evidence` API отклонит 422-й — писать не «не подтвердилось»,
а что именно проверили и что увидели.

### 6. Чинить только подтверждённую причину

Дальше — обычный процесс проекта: TDD, где применимо, полный прогон
`pytest` / `npx tsc --noEmit` / `npx vitest run`, живая проверка в
браузере (Playwright MCP, если доступен). Никакого автомёржа мимо
существующих тестов.

### 7. Коммит — и стоп

Закоммитить фикс с обычным для репозитория форматом сообщения
(`fix: <по-русски, что было не так>`). **Не пушить в прод без явного ОК
пользователя** — задеплоить можно только после того, как он подтвердил.
Исключение — если пользователь заранее выдал более широкий мандат на
автономный деплой для конкретной сессии; по умолчанию не выдан.

Перевести тикет в `fix_ready` можно и до пуша/деплоя — статус описывает
готовность решения, а не факт выката:

```bash
curl -s -X POST "$API/admin/tickets/<id>/events" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status": "fix_ready", "message": "Причина: CORS бакета не разрешал текущий origin фронтенда. Добавили origin в AllowedOrigins."}'
```

Если гипотез недостаточно или не все закрыты, API вернёт 409 с понятной
причиной — это и есть срабатывание правила из «Зачем это нужно».

### 8. После деплоя — событие `deployed`

```bash
curl -s -X POST "$API/admin/tickets/<id>/events" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"status": "deployed", "message": "Выкатили на прод, проверили — загрузка проходит."}'
```

`deployed` доступен только из `fix_ready` — диагноз нельзя перепрыгнуть
даже случайно.

## Уведомление администратора

При создании тикета пользователем бэкенд сам пишет в Telegram
(`ADMIN_TELEGRAM_CHAT_ID` в `.env`) — если переменная не задана, алерта не
будет, но тикет всё равно создастся и будет виден в `/admin/tickets`.
Если работаете в открытой сессии Claude Code без внешнего триггера —
проверять `/admin/tickets?status=new` в начале сессии и по запросу
пользователя.
